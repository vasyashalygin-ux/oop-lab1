## Задание 1. Графический редактор

### Модель

```
            Shape (абстрактный класс, общий контракт)
     ┌────────┬─────┴─────┬──────────┐
  Circle  Rectangle   Segment     Group ──содержит──> Shape (любые, в т.ч. Group)

  Editor ──хранит──> vector<shared_ptr<Shape>>   (порядок = порядок наложения)

  Значения: Vector2D, Point2D, Rect   (иммутабельные, с перегруженными операторами)
```

Контракт `Shape`: `boundingBox()`, `move(v)`, `contains(p)`, `toString()`,
плюс `symbolAt(p)` для отрисовки и `includes(other)` для проверки вложенности.

### Где какие принципы ООП

| Принцип | Где в коде |
|---|---|
| Инкапсуляция | все поля `private`; доступ через методы. Радиус нельзя сделать ≤ 0, отрезок — нулевой длины: проверка в конструкторе. Поле `group_` может менять только `Group` (`friend`). |
| Наследование | `Circle`, `Rectangle`, `Segment`, `Group` **являются** `Shape`. Наследование выражает отношение типов, а не «переиспользование кода». `Rectangle` **содержит** `Rect` — это композиция, не наследование. |
| Полиморфизм по подтипу | `Editor` и `Group` работают только через `Shape` (виртуальные методы). Добавить новую фигуру (например, треугольник) = написать новый класс; `Editor` не меняется (принцип открытости/закрытости). |
| Специализированный (ad-hoc) полиморфизм | перегрузка операторов: `Point2D - Point2D -> Vector2D`, но `Point2D - Vector2D -> Point2D`; `Vector2D * double` и `double * Vector2D`. Одно имя операции — разное поведение в зависимости от типов аргументов. |
| Иммутабельность | у `Vector2D`, `Point2D`, `Rect` нет методов, меняющих объект. `a + b` возвращает новый объект, `a` остаётся прежним (это проверяется тестами). |

### Требования варианта → реализация

| Требование | Реализация |
|---|---|
| окружность, прямоугольник, отрезок | `Circle`, `Rectangle`, `Segment` |
| точка в окружности/прямоугольнике — внутри или на границе | сравнение с `EPS` в `contains` |
| точка на отрезке — расстояние ≤ погрешности | `Segment::distanceTo` (проекция на отрезок с «зажимом» в [0;1]) |
| `Point+Vector`, `Point-Point`, `Vector±Vector`, `Vector*k`, `Vector/k`, `==`, `!=` | `geometry.h` |
| `Rect & Rect` с возможностью узнать, есть ли общая область | возвращает `std::optional<Rect>`: пусто — пересечения нет |
| одна коллекция разных объектов | `std::vector<std::shared_ptr<Shape>>` в `Editor` |
| порядок наложения | позже добавлен = выше; `topAt` идёт с конца вектора |
| добавить / удалить / переместить | `add`, `remove`, `move` |
| верхний объект в точке | `topAt` |
| объекты, чьи bbox пересекаются с областью | `inArea` |
| переместить все объекты в области — той же логикой | `moveInArea` вызывает `inArea` |
| отображение в консоли с учётом наложения | `render` — для каждой клетки берёт `topAt` |
| группа: bbox по всем, move всех, contains — хотя бы один, toString с детьми | `Group` (паттерн «Компоновщик») |
| объект не может быть в двух группах | поле `group_` у `Shape`; `Group::add` проверяет `isInGroup()` |
| группа не содержит себя прямо или косвенно | `Group::add` проверяет `item->includes(this)` |

### Модель владения

Объекты лежат в `std::shared_ptr`: редактор и группа владеют ими совместно с
пользовательским кодом (в `main` мы держим указатель, чтобы потом двигать/удалять объект).
`Shape::group_` — обычный указатель **без владения**: он лишь отмечает,
в какой группе объект. При уничтожении группы он сбрасывается в `nullptr`.

### Какие были варианты реализации (спросят на защите)

- **`unique_ptr` вместо `shared_ptr`.** Тогда «один объект — одна группа» выполнялось бы
  само собой (владелец один), но `remove`/`move` пришлось бы делать по индексу или по
  сырому указателю. Выбран `shared_ptr` — проще API.
- **Результат `Rect & Rect`.** Можно было вернуть `bool` (теряется сама область),
  пустой `Rect` с флагом или бросать исключение. `std::optional` — стандартный способ
  сказать «значения может не быть».
- **Иммутабельность через `const`-поля.** Тогда объект нельзя присвоить, и `Circle::move`
  не смог бы заменить центр. Выбран вариант «private-поля + только const-методы».
- **Проверка циклов через `dynamic_cast<Group*>`.** Работает, но это проверка конкретного
  типа. Виртуальный `includes` — полиморфное решение без знания о типах.
- **Отрисовка.** Можно было «рисовать» объекты по очереди снизу вверх поверх друг друга;
  выбран вариант через `topAt`, чтобы использовать одну логику наложения.
- **Касание прямоугольников по стороне** считается пересечением (вырожденная область),
  т.к. граница принадлежит прямоугольнику — так же, как в `contains`.

### Возможные вопросы

- *Почему деструктор `Shape` виртуальный?* — Объекты удаляются через указатель на базовый
  класс; без `virtual` вызвался бы только `~Shape`, и `~Group` не отработал бы.
- *Почему у `Group` запрещено копирование?* — Копия содержала бы те же объекты,
  и они оказались бы в двух группах.
- *Зачем `EPS`?* — `0.1 + 0.2 != 0.3` в `double`, сравнивать вещественные числа нужно с погрешностью.
- *Зачем `friend class Group`?* — Чтобы отметку о группе мог менять только `Group`,
  а не любой внешний код (это и есть инкапсуляция инварианта «одна группа»).
- *Статические методы?* — Не используются. Единственная свободная функция
  `operator*(double, Vector2D)` нужна, потому что левый операнд — `double`, а не наш класс.

## Задание 2. Планировщик задач

### Модель

```
BinaryHeap<T, Compare>        общая структура, не знает про задачи
        ▲ используется
Scheduler<Rule>               предметная логика: id, выполнение, executeAll
   Rule = ByPriority | ByDeadline   (функторы, передаются параметром шаблона)
Task                          иммутабельная задача: id, name, priority, deadline
```

### Двоичная куча

- Хранилище — `std::vector<T>` (разрешено как вспомогательный контейнер).
  Полное бинарное дерево уложено по уровням: родитель `(i-1)/2`, сыновья `2i+1`, `2i+2`.
- `Compare(a, b) == true` ⇔ `a` приоритетнее `b` (ближе к вершине).
  `std::less<int>` → на вершине минимум, `std::greater<int>` → максимум.
- `push` — в конец + просеивание вверх, O(log n).
  `pop` — вершину заменяем последним + просеивание вниз, O(log n). `top` — O(1).
- Пустая куча: `top`/`pop` бросают `std::out_of_range`.

**Инварианты:**
1. Дерево полное — выполняется автоматически: элементы лежат в векторе подряд, без «дыр».
2. Свойство кучи: для любого `i > 0` элемент не приоритетнее родителя:
   `!compare(data[i], data[parent(i)])`. Его восстанавливают `siftUp`/`siftDown`;
   метод `isValid()` проверяет это в тестах после каждой операции.

Поля `private`, снаружи доступны только `push/top/pop/size/empty`, поэтому
сломать инвариант извне нельзя.

### Требования варианта → реализация

| Требование | Реализация |
|---|---|
| куча — общий тип, не зависит от задачи | `BinaryHeap<T, Compare>`; в тестах используется с `int` и `std::string` |
| правило порядка не зашито в кучу | параметр `Compare` |
| добавить, посмотреть без удаления, извлечь, размер, проверка на пустоту | `push`, `top`, `pop`, `size`, `empty` |
| `std::priority_queue` не используется | вся логика — `siftUp`/`siftDown` |
| добавить задачу, следующая задача, выполнить, количество, выполнить все | `addTask`, `peekNext`, `executeNext`, `pendingCount`, `executeAll` |
| два правила, смена правила без изменения кучи | `ByPriority`, `ByDeadline` в `rules.h` |
| поведение при равенстве определено явно | при равном критерии раньше задача с **меньшим id** — порядок всегда однозначный |
| уникальный id | `std::set<int>` ожидающих id; повтор → исключение. После выполнения id освобождается |
| работа с пустым планировщиком | `peekNext`/`executeNext` бросают `std::logic_error` |

### Модель владения

Куча хранит элементы **по значению** (`std::vector<T>`) и полностью ими владеет.
Указателей нет вообще, поэтому нет и вопросов с утечками/висячими указателями.
`Task` — небольшое иммутабельное значение, копировать его дёшево.

### Какие были варианты реализации

- **Правило через `std::function<bool(const T&, const T&)>`** вместо параметра шаблона —
  можно менять правило во время работы, но медленнее и тип кучи один для всех правил.
- **Куча на узлах с указателями** вместо массива — сложнее, нужно управлять памятью
  и искать последний узел; массив проще и быстрее.
- **Равные элементы.** Можно было не определять порядок (куча не стабильна) или
  хранить счётчик добавления, чтобы сохранять FIFO. Выбран tie-break по id.
- **Освобождение id после выполнения.** Альтернатива — запрещать id навсегда (хранить историю).

### Возможные вопросы

- *Почему куча не стабильна?* — `siftDown` меняет местами элементы через уровни, порядок
  равных нарушается. Поэтому правило равенства задано явно в функторах.
- *Сложность построения из n элементов?* — n вызовов `push` = O(n log n)
  (есть алгоритм heapify за O(n), здесь не требовался).
- *Почему шаблон целиком в `.h`?* — Компилятор должен видеть тело шаблона при
  подстановке конкретного типа.
- *Чем `Compare` отличается от `std::priority_queue`?* — Там `std::less` даёт максимум
  на вершине; здесь `compare(a,b)` читается как «a важнее b», так нагляднее.
